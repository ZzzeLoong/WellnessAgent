# WellnessAgent 演进需求文档

> 版本：v0.2（基于 HelloAgents v1.0.0 上游更新修订）
> 状态：待评审
> 范围：本文只描述**需求、价值、验收标准、分期与工作量**，**不包含技术方案**。技术方案将在需求评审通过后，针对每个功能单独输出设计文档。
>
> **与 HelloAgents 上游关系**：WellnessAgent 基于 [HelloAgents](https://github.com/jjyaoao/HelloAgents) v1.0.0 作为上游基础框架。HelloAgents 提供了 Function Calling、Streaming、Context Management、Trace Logging、Sub-Agent（TaskTool/ToolFilter）、Circuit Breaker、Session 持久化等通用能力；WellnessAgent 在此基础上聚焦**健康饮食场景的差异化**：Guardrails 安全校验、多层记忆、RAG、多模态识餐、主动推送、执行反馈闭环等。本文中标注 `🔥上游可复用` 的需求表示 HelloAgents 已有成熟实现可参考/适配，工作量已相应下调。

---

## 0. 文档说明

### 0.1 目标

将 WellnessAgent 从"单体 ReAct + 记忆 + RAG 的问答型 agent"演进为一个**对标 2025 年 agent 标准**、并具备**差异化亮点**的个人健康饮食智能体，使其成为一个高质量的作品集项目（portfolio）。

### 0.2 工作量单位说明（T-shirt Size）

本文用 T-shirt size 表示**相对工作量**，不代表绝对工时。参考换算（仅供直觉）：

| Size | 相对含义 | 直觉参考 |
|------|---------|---------|
| **S** | 小改动，局部、低风险 | 半天内 |
| **M** | 中等，涉及一个模块的新增/改造 | 1–2 天 |
| **L** | 较大，跨多个模块或引入新架构层 | 3–5 天 |
| **XL** | 大型，架构级改造或需要多轮验证 | 1 周以上 |

1. 第 1 章：项目现状基线（已实现能力 + 现存缺陷）
2. 第 2 章：需求清单（分三期）
3. 第 3 章：分期路线图与依赖关系
4. 第 4 章：工作量汇总

## 1. 项目现状基线

### 1.1 已实现能力

| 模块 | 现状 | 位置 |
|------|------|------|
| **ReAct 循环** | JSON 协议优先、文本解析回退的单步推理-行动循环 | `agents/react_agent.py` |
| **LLM 统一接口** | 支持多 provider（OpenAI/DeepSeek/Qwen/Kimi/Zhipu/Ollama 等），含同步 `invoke` 与流式 `think`/`stream_invoke` | `core/llm.py` |
| **多层记忆** | 工作记忆（内存+TTL）、情景记忆（SQLite 权威 + Qdrant 向量）、语义记忆、感知记忆框架 | `memory/types/`、`memory/manager.py` |
| **RAG** | 多格式文档解析、向量检索、MQE/HyDE 高级检索、命名空间隔离、引用来源 | `tools/builtin/rag_tool.py`、`memory/rag/` |
| **业务 Agent** | 画像 CRUD、短期上下文、长期记忆提纯（distill）、知识库问答 | `wellnessagent/agent.py`、`wellnessagent/service.py` |
| **Web 服务** | FastAPI 提供 chat/state/profile/knowledgebase/memory 接口 + React 调试前端 | `wellnessagent/server/`、`frontend/` |
| **评测框架** | 20 个 benchmark task + 多个 evaluator（硬约束/RAG grounding/状态跟踪/工具使用/replanning/LLM judge）+ 多个 baseline | `benchmark/` |

### 1.2 现存缺陷（技术债）

| 编号 | 缺陷 | 影响 | 位置 |
|------|------|------|------|
| **D1** | ReAct 循环与 `/api/chat` 只用同步 `invoke`，流式能力闲置 | 用户等待整轮跑完才有反馈，体验差 | `agents/react_agent.py`、`server/main.py` |
| **D2** | 工具调用基于"LLM 返回 JSON → 手动解析"，未使用原生 `tools`/`tool_calls` | 解析仍可能失败，可靠性受模型输出格式影响 | `agents/react_agent.py` |
| **D3** | `_AGENTS` 全局字典无上限、无淘汰 | 多用户长期运行内存持续增长 | `wellnessagent/server/deps.py` |
| **D4** | `Message.timestamp` 默认值处理不当（`= None` 与 Pydantic 校验冲突） | 潜在校验/时间戳错误 | `core/message.py` |
| **D5** | ReAct trace（`StepRecord`）只在返回值中，不落盘、不结构化存储 | 无法回放、无法排查线上问题、无法做质量分析 | `agents/react_agent.py` |
| **D6** | 无任何输出安全校验层 | 健康建议可能触碰过敏原/给出不安全建议 | 全局缺失 |
| **D7** | 感知记忆仅存 `file_path`，无真正的视觉理解 | 多模态是"占位"而非"能力" | `tools/builtin/memory_tool.py` |
| **D8** | 知识库 seed 每进程每用户重复触发判断，缺少幂等落盘标记 | 重复 seed / 冷启动慢 | `wellnessagent/server/deps.py` |
| **D9** | 无上下文窗口管理，长对话易超 token 限制导致截断或报错 | 复杂多轮对话不可靠 | 全局缺失（🔥上游 `HistoryManager` + `TokenCounter` + `ObservationTruncator` 可复用） |
| **D10** | 工具失败无熔断保护，可能无限重试导致死循环 | 工具异常时 agent 行为不可预测 | 全局缺失（🔥上游 `CircuitBreaker` 可复用） |
| **D11** | 无会话持久化，服务重启后对话状态丢失 | 用户体验断裂 | 全局缺失（🔥上游 `SessionStore` 可复用） |

## 2. 需求清单

> 每条需求包含：**背景/价值、需求描述、验收标准、工作量、依赖、所属期**。
> 缺陷修复以 `D#` 关联第 1.2 节。

---

### 第一期：止血（工程稳健性）

目标：**打好地基**——让工具调用可靠、输出安全、体验达标、消除已知技术债。这一期不引入新架构层，只让"现在的东西更稳"。得益于 HelloAgents 上游复用，本期多项工作量已下调，整体节奏可加快。

---

#### R1. 原生 Function Calling 改造 🔥上游可复用

- **背景/价值**：当前依赖模型按约定输出 JSON 再手动解析（D2），可靠性受模型输出格式波动影响。原生 `tools` / `tool_calls` 协议是 2025 年主流标准，可靠性显著更高，也是后续 SubAgent 的地基。
- **上游参考**：HelloAgents `core/llm.py` 的 `invoke_with_tools()` + `core/llm_adapters.py` 多 provider 适配 + `agents/react_agent.py` 的 `Thought`/`Finish` 结构化工具模式，已完整实现原生 Function Calling 与文本回退双路径。
- **需求描述**：
  - 工具定义能以标准 schema（名称/描述/参数）暴露给 LLM。
  - ReAct 循环支持消费模型返回的原生工具调用结构，替代/兼容现有文本-JSON 解析。
  - 对不支持原生 function calling 的 provider 保留回退路径。
  - 工具调用结果使用 `ToolResponse` 标准协议（SUCCESS/PARTIAL/ERROR）。
- **验收标准**：
  - 在支持的 provider 上，工具调用不再依赖文本正则解析即可稳定触发。
  - 现有 benchmark 的工具使用类评测得分不低于改造前。
  - 至少 1 个不支持原生协议的 provider 走回退路径且可用。
  - 工具执行失败返回 `ToolResponse.ERROR` 而非裸异常。
- **工作量**：**M**（上游已有成熟实现，主要工作为适配 WellnessAgent 现有工具体系与记忆系统）
- **依赖**：无（其他多项功能依赖它）
- **关联缺陷**：D2

---

#### R2. 流式输出（Streaming / SSE） 🔥上游可复用

- **背景/价值**：当前整轮跑完才返回（D1），用户长时间无反馈。流式是体验底线。
- **上游参考**：HelloAgents `core/streaming.py` 的 `StreamEvent` + `stream_to_sse()` + `agents/react_agent.py` 的 `arun_stream()` 异步生成器模式，已完整实现 SSE 流式输出。
- **需求描述**：
  - `/api/chat` 支持以流式方式增量返回：至少包含"思考中/工具调用中/最终答案增量"三类事件。
  - 前端调试台能实时展示流式过程。
- **验收标准**：
  - 首个可见反馈时间显著早于最终答案完成时间。
  - 前端能逐步渲染答案与中间步骤，不出现整段等待。
  - 流式中断/报错有明确的前端提示。
- **工作量**：**S**（上游 `StreamEvent`/`stream_to_sse` 可直接复用，仅需接入 FastAPI 的 `StreamingResponse`）
- **依赖**：R1（可并行，但建议 R1 先行以复用统一事件）
- **关联缺陷**：D1

---

#### R3. Guardrails 安全校验层

- **背景/价值**：健康饮食场景的**红线**——不能给出触碰用户过敏原或明显不安全的建议（D6）。这是本项目区别于"通用 chatbot"的责任边界。
- **需求描述**：
  - 输出前进行安全校验：结合用户画像（过敏原、忌口、医疗备注）检查最终建议。
  - 命中风险时能拦截或改写，并向用户明确提示原因。
  - 校验结果计入 trace，便于审计。
- **验收标准**：
  - 构造包含过敏原的诱导性问题时，最终输出不会推荐该过敏原，或明确警示。
  - 拦截/改写事件在 trace 中可见。
  - 正常无风险请求不被误伤（误拦率可接受）。
- **工作量**：**M**
- **依赖**：R5（trace 落盘，便于审计；非强依赖）
- **关联缺陷**：D6

---

#### R4. 现存缺陷修复合集

- **背景/价值**：清理已知技术债，避免在其上继续叠加新功能。
- **需求描述**（对应缺陷）：
  - 修复 `Message.timestamp` 默认值问题（D4）。
  - `_AGENTS` 引入上限与淘汰策略，避免内存无界增长（D3）。
  - 知识库 seed 幂等化，避免重复初始化（D8）。
- **验收标准**：
  - 构造消息不再出现时间戳相关校验异常。
  - 大量不同 user_id 访问后，Agent 缓存规模受控。
  - 重复触发 seed 不产生重复数据、冷启动可接受。
- **工作量**：**S**
- **依赖**：无
- **关联缺陷**：D3、D4、D8

---

#### R5. 可观测性：Trace 落盘与结构化 🔥上游可复用

- **背景/价值**：当前 trace 不持久化（D5），无法回放和分析。可观测性是"能长期维护"的前提，也是后续 A/B、质量分析的数据来源。
- **上游参考**：HelloAgents `observability/trace_logger.py` 已实现 JSONL + HTML 双格式落盘、自动脱敏、统计汇总，可直接适配。
- **需求描述**：
  - 每轮对话的完整 trace（步骤、工具调用、观察、耗时、终止原因）结构化持久化。
  - 支持按 user_id / 会话检索历史 trace。
  - 提供最小化的查看入口（可先接入调试前端）。
- **验收标准**：
  - 一轮对话结束后可在存储中查到完整结构化 trace。
  - 能按用户/会话回放某一轮的推理过程。
- **工作量**：**S**（上游 `TraceLogger` 可直接复用，仅需适配 WellnessAgent 的 trace 数据结构）
- **依赖**：无（R3、AB 实验会消费它）
- **关联缺陷**：D5

---

### 第二期：架构（能力上限）

目标：**突破单体 agent 的复杂度天花板**，引入编排层与人机协同，让复杂请求（多约束、多目标）也能稳定完成。

---

#### R6. Orchestrator + SubAgent 架构 🔥上游可复用（部分）

- **背景/价值**：单体 agent 在"7 天减脂食谱 + 避开多个过敏原 + 时间约束 + 预算约束"这类复合请求上容易走偏或漏约束。引入编排层，把任务拆解给专职 SubAgent（如画像/食谱/知识检索/安全），是能力上限的关键。
- **上游参考**：HelloAgents `tools/builtin/task_tool.py`（`TaskTool` 隔离子 agent执行）+ `tools/tool_filter.py`（`ReadOnlyFilter`/`FullAccessFilter` 权限控制）+ `agents/react_agent.py`（结构化 Thought/Finish 工具），Sub-Agent 的隔离执行与权限过滤机制已可复用。**Orchestrator 编排逻辑（意图理解→任务拆解→分派→汇总）为 WellnessAgent 自研差异化部分。**
- **需求描述**：
  - 有一个编排者（Orchestrator）负责：意图理解 → 任务拆解 → 分派 → 汇总。
  - 至少落地一组专职 SubAgent（建议：画像、饮食规划、知识检索、安全检查）。
  - 支持子任务的顺序/并行执行与结果聚合。
  - SubAgent 通过 `TaskTool` 隔离执行，通过 `ToolFilter` 控制工具访问权限。
- **验收标准**：
  - 复合请求能被拆解为可见的子任务并逐一完成。
  - 相比单体版本，复合请求的约束遵守率（如过敏原遵守、时间/预算约束）不下降且可度量提升。
  - 编排过程在 trace 中可见（子任务、分派、聚合）。
  - SubAgent 只能访问被授权的工具子集。
- **工作量**：**L**（上游 `TaskTool`/`ToolFilter` 可复用，Orchestrator 编排逻辑为自研，整体从 XL 下调）
- **依赖**：R1（工具调用可靠）、R5（trace）、R15（上下文管理）
- **关联缺陷**：—

---

#### R7. Human-in-the-Loop（人机协同确认）

- **背景/价值**：健康建议在关键决策点（如涉及过敏/身体状况变化）应允许用户确认或修正，形成安全闭环。
- **需求描述**：
  - 在高风险或高影响步骤支持"暂停 → 请求用户确认/补充 → 继续"。
  - 用户可在中途修正约束（如临时补充一条忌口），agent 据此调整。
- **验收标准**：
  - 触发确认节点时，流程能正确暂停并在用户响应后继续。
  - 用户中途修正能实际影响后续输出。
- **工作量**：**L**
- **依赖**：R2（流式/交互）、R6（编排层）
- **关联缺陷**：—

---

#### R8. 可观测性增强：指标与质量分析

- **背景/价值**：在 R5 落盘基础上，进一步沉淀可分析的指标，为持续优化和 A/B 提供依据。
- **需求描述**：
  - 汇总关键指标：每轮步数、工具调用次数、终止原因分布、安全拦截次数、时延等。
  - 提供最小化的汇总视图（可接入前端或输出报表）。
- **验收标准**：
  - 能查看一段时间内的关键指标汇总。
  - 指标口径清晰、可复现。
- **工作量**：**M**
- **依赖**：R5
- **关联缺陷**：D5（延续）

---

### 第三期：差异化（亮点）

目标：**做出别人没有的亮点**，把"健康 + 记忆 + 时间"的组合价值最大化，形成 portfolio 记忆点。

---

#### R9. 多模态：拍照识餐

- **背景/价值**：用户拍一张食物照片即可获得识别与风险提示，是健康场景最直观的 wow feature，也让现有感知记忆（D7）从"占位"变成"能力"。
- **需求描述**：
  - 支持图片输入：识别食物、估算营养/热量区间、结合画像给出过敏/忌口风险提示。
  - 识别结果可写入感知记忆并被后续对话引用。
- **验收标准**：
  - 上传常见食物照片能得到合理的识别与风险提示。
  - 命中用户过敏原的食物能被明确警示（与 R3 联动）。
  - 识别记录可在后续对话中被检索/引用。
- **工作量**：**L**
- **依赖**：R3（安全联动）、感知记忆现有框架
- **关联缺陷**：D7

---

#### R10. 主动推送（Proactive Agent）

- **背景/价值**：从"被动问答"升级为"主动关心"——按用户画像与近期反馈，定时主动推送当日饮食建议，是健康助手的核心差异。
- **需求描述**：
  - 支持按计划（如每日固定时间）生成并推送当日建议。
  - 推送内容结合画像、长期记忆、近期反馈。
  - 用户可开启/关闭、调整频率。
- **验收标准**：
  - 到达设定时间能生成并送达个性化建议。
  - 建议明显反映用户画像与近期反馈，而非通用模板。
  - 可被用户开关与配置。
- **工作量**：**L**
- **依赖**：R6（编排复用）、R5（依据历史）
- **关联缺陷**：—

---

#### R11. 执行反馈闭环（Plan → Execute → Feedback）

- **背景/价值**：给出建议后跟踪执行情况，下次主动回访（"昨天那个食谱怎么样？"），让个性化真正随时间进化。
- **需求描述**：
  - 记录已给出的建议及其状态（是否采纳、反馈如何）。
  - 后续对话或推送中主动回访，并据反馈调整策略。
- **验收标准**：
  - 一次建议后，系统能在后续交互中引用并询问其结果。
  - 用户反馈能实际改变后续建议倾向。
- **工作量**：**M**
- **依赖**：R5、R10
- **关联缺陷**：—

---

#### R12. 记忆可视化时间线

- **背景/价值**：把"四层记忆"做成可交互的时间线视图，比纯文字 demo 直观得多，是展示记忆架构的杀手锏。
- **需求描述**：
  - 前端以时间轴展示 working / episodic（含 distilled）记忆的产生与演化。
  - 可按类型/时间筛选，点击查看详情。
- **验收标准**：
  - 能按时间顺序看到记忆的新增/提纯/淘汰。
  - 可区分记忆类型并查看单条详情。
- **工作量**：**M**
- **依赖**：R5（数据来源）
- **关联缺陷**：—

---

#### R13. MCP Server 对外暴露

- **背景/价值**：项目已有 MCP client（`protocols/mcp/`），将 WellnessAgent 能力注册为 MCP Server，即可被任意 MCP 兼容客户端调用，符合 2025 互操作标准。
- **需求描述**：
  - 将核心能力（如知识问答、画像查询、饮食规划）以 MCP Server 形式暴露。
  - 提供最小接入示例。
- **验收标准**：
  - 一个 MCP 兼容客户端能发现并调用暴露的能力。
  - 有可运行的接入示例。
- **工作量**：**M**
- **依赖**：R6（能力边界清晰后更易暴露）
- **关联缺陷**：—

#### R14. Benchmark 扩展：A/B 实验与新 Evaluator

- **背景/价值**：项目已有较完整评测框架，A/B 对比（不同 prompt / model / 有无 memory / 单体 vs 编排）是量化证明改进价值的最佳方式，也是 portfolio 的硬核论据。
- **需求描述**：
  - 支持在相同 task 集上对多种配置做 A/B 对比并产出对照报告。
  - 针对新功能补充 evaluator（如安全拦截有效性、编排约束遵守率、流式体验相关指标）。
- **验收标准**：
  - 能一键跑出两种以上配置的对照结果并生成报告。
  - 新增 evaluator 有明确口径且结果可复现。
- **工作量**：**L**
- **依赖**：R5/R8（指标与数据）、R3/R6（被评测对象）
- **关联缺陷**：—

---

#### R15. 上下文工程（Context Engineering） 🔥上游可复用

- **背景/价值**：当前无上下文窗口管理（D9），长对话易超 token 限制导致截断或报错。上下文工程是 2025 年 agent 的核心能力，直接影响推理质量和成本。
- **上游参考**：HelloAgents `context/history.py`（`HistoryManager` 消息压缩与轮次检测）+ `context/token_counter.py`（`TokenCounter` 增量计数与缓存）+ `context/observation_truncator.py`（`ObservationTruncator` 工具输出截断），三组件协同完成上下文窗口管理。
- **需求描述**：
  - 引入 `TokenCounter`，对所有发往 LLM 的消息做准确的 token 计数（含缓存与增量计数）。
  - 引入 `HistoryManager`，在接近上下文窗口上限时自动压缩历史消息（摘要/截断策略）。
  - 引入 `ObservationTruncator`，对过长的工具输出做智能截断，保留关键信息。
- **验收标准**：
  - 长对话不再因超 token 报错，而是自动压缩后继续。
  - 压缩后的对话质量不显著下降（benchmark 得分可接受范围）。
  - token 计数与实际消耗偏差 < 5%。
- **工作量**：**M**（上游三组件可直接复用，需适配 WellnessAgent 的消息格式与记忆系统）
- **依赖**：R1（消息结构统一后更易集成）
- **关联缺陷**：D9

---

#### R16. 熔断器（Circuit Breaker） 🔥上游可复用

- **背景/价值**：工具失败无熔断保护（D10），可能无限重试导致死循环或资源浪费。熔断器是 agent 稳定性的关键保障，也是 R6 SubAgent 的依赖项。
- **上游参考**：HelloAgents `tools/circuit_breaker.py` 已实现完整的熔断器模式（Closed→Open→Half-Open 状态机、可配置阈值与恢复时间）。
- **需求描述**：
  - 为每个工具实例配置熔断器，连续失败超过阈值后自动熔断。
  - 熔断期间跳过该工具调用并返回 `ToolResponse.ERROR`，避免无效重试。
  - 支持配置熔断阈值、恢复时间等参数。
  - 熔断事件计入 trace。
- **验收标准**：
  - 工具连续失败 N 次后，后续调用被熔断跳过。
  - 熔断恢复后工具可正常调用。
  - 熔断事件在 trace 中可见。
- **工作量**：**S**（上游 `CircuitBreaker` 可直接复用，仅需配置接入）
- **依赖**：R1（ToolResponse 协议）
- **关联缺陷**：D10
